# IMP-01.05 — Publish and retrieve catalog lineage

Status: proposed; not implemented by this review.
Priority: P1 — missing 03.10 acceptance.
Dependencies: None.

## Evidence and impact

`register_seed()` ignores seed lineage. The seed names raw train/test inputs and a curated output, but no lineage API call creates those edges. The live test checks a table by name and owner, not lineage or indexed discovery.

Read [the review README](README.md) first. Recheck these observations against the working tree before implementation.

## Proposed allowed paths

`clusters/dev/openmetadata/register_baseline_metadata.py`; `clusters/dev/openmetadata/catalog-seed-configmap.yaml`; `tests/integration/openmetadata/**`; `docs/runbooks/openmetadata.md`.

## Bounded implementation steps

Use the pinned OpenMetadata schema to represent the two raw assets, curated table and ingestion job/run linkage. Document the chosen entity types before coding. Register directed raw-to-curated edges with the producing run and immutable lakeFS commit reference. Consume explicit manifest/event inputs. Verify table lookup by owner/name and indexed search separately if discoverability is claimed.

## Acceptance and verification

Mock tests assert exact edge direction, stable identifiers and retry without duplicate edges. A live test retrieves lineage from the API and follows both inputs to the curated output and run reference. Do not count ConfigMap contents as evidence of catalog registration.

## Non-goals and stop conditions

Do not build a general OpenLineage ingestion service here. That can follow after one real run is demonstrably navigable.

If a required API, fixture, version or permission is unavailable, report the exact blocker. Do not fabricate a successful result. Hand off changed files, verification mode/outcomes and remaining risks; commit/push only when requested.
