# IMP-05.03 — Prove a commit actually runs through Woodpecker

Status: proposed; not implemented by this review.
Priority: P2 — before calling CI delivery complete.
Dependencies: None.

## Evidence and impact

`tests/integration/ci/test_ci.py` builds and pushes a tiny image from the host and checks robot permissions. The CI runbook explicitly defers Forgejo OAuth/webhook activation. This is useful identity coverage but not a repository-triggered pipeline execution.

Read [the review README](README.md) first. Recheck these observations against the working tree before implementation.

## Proposed allowed paths

`clusters/dev/ci/**`; `platform/charts/woodpecker/**`; `platform/charts/forgejo/**`; `tests/integration/ci/**`; `docs/runbooks/ci.md`.

## Bounded implementation steps

Create a dedicated local fixture repository and wire its webhook to Woodpecker. Define one tiny pipeline using the existing build/test/signing primitives where already compatible. Begin with a failing and a passing test-only commit before adding registry publication. Record the actual CI run ID and source commit, with logs retrieved from Woodpecker. Keep GitHub/Forgejo source-of-truth boundaries explicit.

## Acceptance and verification

An authorized live test submits one passing and one failing fixture commit and verifies distinct CI statuses for those exact SHAs. Untrusted work must not receive push credentials. Delete only test-owned credentials/resources in cleanup; report retained artifacts.

## Non-goals and stop conditions

Do not migrate the main repository, push the user's branch, or equate a host Docker push with a CI run. GitOps expansion comes after this small path works.

If a required API, fixture, version or permission is unavailable, report the exact blocker. Do not fabricate a successful result. Hand off changed files, verification mode/outcomes and remaining risks; commit/push only when requested.
