# IMP-03.03 — Make readiness mean the pinned model can serve

Status: proposed; not implemented by this review.
Priority: P2 — before treating the API as deployable.
Dependencies: None.

## Evidence and impact

`service/app.py` returns OK from /healthz before settings are validated or the lazy model loader has succeeded. The first request may fail; concurrent initial requests can load the model multiple times. Positive probability is assumed to occupy column index one.

Read [the review README](README.md) first. Recheck these observations against the working tree before implementation.

## Proposed allowed paths

`examples/sklearn_baseline/service/app.py`; `examples/sklearn_baseline/tests/test_service.py`; `compose.yaml` (serving probe only); `examples/sklearn_baseline/README.md`.

## Bounded implementation steps

Keep liveness separate from readiness. Load and validate the explicitly selected model in application lifespan or guard lazy loading against concurrency. Return not-ready until loading succeeds; expose a sanitized unavailable response on failure. Select the probability column using model.classes_ for label 1. Reject non-finite numeric input.

## Acceptance and verification

Use fake loaders for failure, a slow concurrent load and reversed class order. Assert only one initialization, correct class-1 probability, not-ready behavior and normal successful prediction. Run `.venv/bin/python -m pytest examples/sklearn_baseline/tests/test_service.py` in the declared baseline environment.

## Non-goals and stop conditions

Do not add Kubernetes serving or autoscaling; later Phase 5 owns that. Do not weaken exact-version selection.

If a required API, fixture, version or permission is unavailable, report the exact blocker. Do not fabricate a successful result. Hand off changed files, verification mode/outcomes and remaining risks; commit/push only when requested.
