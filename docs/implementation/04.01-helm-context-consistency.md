# IMP-04.01 — Bind Helm and kubectl to the same cluster

Status: proposed; not implemented by this review.
Priority: P1 — before the next deployment refactor.
Dependencies: None.

## Evidence and impact

Makefile kubectl calls usually specify kind context. Helm invocations, including the Docker fallback, generally do not specify --kube-context. Mounting a kubeconfig file does not select the intended context within it.

Read [the review README](README.md) first. Recheck these observations against the working tree before implementation.

## Proposed allowed paths

`Makefile`; new `scripts/cluster/helm-study.sh`; new `tests/unit/cluster/test_helm_study.py`; `docs/runbooks/cluster.md`.

## Bounded implementation steps

Introduce a small Helm wrapper used by the OpenMetadata recipes first. Pass the expected kube-context in both native and container routes. Resolve and verify the exact kubeconfig and expected cluster before a mutating command. Pass arguments as arrays; do not evaluate shell-generated strings. Document a follow-up migration for other Helm recipes rather than rewriting the entire Makefile in one task.

## Acceptance and verification

Fake-command tests with a kubeconfig whose current context is deliberately different must show the explicit intended context reaches Helm. Test native and container paths, missing kubeconfig and missing context. No live mutation is needed for this test.

## Non-goals and stop conditions

Do not rewrite the user's global current context, initialize another cluster, or log kubeconfig credentials.

If a required API, fixture, version or permission is unavailable, report the exact blocker. Do not fabricate a successful result. Hand off changed files, verification mode/outcomes and remaining risks; commit/push only when requested.
